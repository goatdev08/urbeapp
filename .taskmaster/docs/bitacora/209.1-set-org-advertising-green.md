## GREEN — subtarea #209.1 (EF set-org-advertising sobre la RPC ya existente)

### Hecho

**Edge Function `set-org-advertising`** (patrón DI, gemelo de `moderate-ad` #208.1):
- `supabase/functions/set-org-advertising/handler.ts` — implementación real. Orden:
  CORS → método → parseo JSON → validación de FORMA del payload (agency_id string,
  enabled boolean, category opcional pero si viene debe pertenecer al enum
  `advertiser_category`) → `adminVerifier.verify_caller` → `orgAdvertisingWriter.set`
  → traducción de `OrgAdvertisingErrorCode` a HTTP (`AGENCY_NOT_FOUND`→404,
  `ADVERTISER_CATEGORY_REQUIRED`→422, `DB_ERROR`→500) → `{ ok: true }` en 200.
  Deliberadamente NO valida "si enabled=true entonces category es obligatoria" —
  esa regla vive en la RPC (CHECK + `raise ADVERTISER_CATEGORY_REQUIRED`).
- `supabase/functions/set-org-advertising/index.ts` (nuevo) — entry point delgado,
  construye `service_client()` + `make_admin_verifier` + `make_org_advertising_writer`
  e inyecta al handler. Cero lógica propia (mismo criterio que moderate-ad/index.ts).
- `supabase/functions/_shared/clients.ts` — nueva factory `make_org_advertising_writer`
  (adaptador real sobre la RPC) + `extract_org_advertising_error_code` (matchea
  AGENCY_NOT_FOUND / ADVERTISER_CATEGORY_REQUIRED en el mensaje de Postgres, cualquier
  otra cosa colapsa a DB_ERROR). Import de tipos de `set-org-advertising/types.ts`
  agregado junto a los demás imports de dominio.

**Migración `set_org_advertising_atomic_admin`** (el problema real señalado por RED):
- `supabase/migrations/20260823000001_set_org_advertising_atomic_admin.sql` — decisión:
  OVERLOAD de 4 argumentos sobre `set_org_advertising_atomic` (mismo nombre, firma
  `(uuid, boolean, advertiser_category, uuid)`), NO una función con nombre nuevo.
  Por qué: es la MISMA operación de negocio ("encender/apagar modo comercial"), solo
  con un parámetro extra para el actor — igual que Postgres ya resuelve
  `set_org_advertising_atomic(id, true)` (3 args, con `p_category default null`)
  vs esta de 4. El overload: (1) instala `p_admin_id` en el GUC
  `urbea.admin_actor_id` con `set_config(..., true)` — local a la transacción — y
  (2) delega el 100% de la validación/UPDATE/auditoría en la RPC de 3 argumentos ya
  existente vía `perform public.set_org_advertising_atomic(p_agency_id, p_enabled,
  p_category)`. CERO lógica de negocio duplicada — a diferencia de `moderate_ad_atomic`
  (#208.1), que sí fue una función nueva desde cero porque no había una RPC de 3
  argumentos previa que envolver; aquí sí la había, así que tocaba delegar, no repetir.
  `security definer`, `set search_path = public, pg_temp`, revoke de
  public/anon/authenticated, grant solo a service_role.
  Aditiva, idempotente (`create or replace`), NO toca la RPC de 3 argumentos ni sus
  grants (los preserva intactos para Studio/CLI).
- `supabase/migrations/rollbacks/20260823000001_set_org_advertising_atomic_admin.sql`
  — `drop function` del overload de 4 argumentos únicamente; documenta que revertir
  con la EF ya desplegada la deja devolviendo 500 (PGRST202), sin pérdida de datos
  ni de auditoría (la escribe la RPC de 3 args, intacta).

**Tests pgTAP** — `supabase/tests/65_set_org_advertising_atomic_admin_test.sql` (9

No se repite la cobertura de metadata de columnas/enum ni la matriz completa de
transiciones — ya vive en `46_org_advertising_test.sql` sección 7 sobre la RPC de 3
argumentos, y este overload delega en ella sin reimplementarla.

### Invariantes cubiertas
- 🔒 La RPC de 3 argumentos sigue siendo la ÚNICA autoridad sobre si encender
  `can_advertise` es válido — el overload y el handler TypeScript no duplican esa
  regla en ningún punto.
- 🔒 `admin_actions` sigue auditando en la MISMA transacción que el UPDATE (lo
  garantiza la RPC de 3 args; el overload no interpone una segunda transacción).
- 🔒 El overload es inalcanzable para `authenticated`/`anon` (instala un admin_actor
  arbitrario en el GUC — escalada de privilegios si no fuera solo `service_role`).
- 🔴 El handler nunca reenvía el texto crudo de Postgres (EC-20): la traducción pasa
  siempre por `OrgAdvertisingErrorCode` + un mensaje propio.

### Gotchas para la bitácora

  con "Cannot connect to the Docker daemon"); `open -a Docker` + esperar ~10s bastó.
- `supabase migration list --local` compara archivos locales vs. migraciones
  aplicadas al proyecto REMOTO (columna "Remote"), NO indica si el stack LOCAL ya
  las corrió — para eso hace falta `supabase migration up --local` (que es idempotente
  y no aplica nada si ya está al día) o consultar directo la tabla de historial.
- No hay `psql` en el PATH de este entorno; `supabase migration up` / `supabase test db`
  son el camino sin necesidad de un cliente Postgres aparte.
- El overload de 4 argumentos se resuelve sin ambigüedad porque `client.rpc(...)`
  pasa los 4 parámetros con nombre exacto (`p_agency_id`, `p_enabled`, `p_category`,
  `p_admin_id>`) — PostgREST/Postgres lo distingue de la firma de 3 argumentos por
  cantidad+nombres, sin necesidad de un nombre de función distinto.
