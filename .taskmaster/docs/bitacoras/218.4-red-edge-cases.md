## 218.4 — RED: test de guardia TS↔SQL del whitelist de campos editables

Enfoque (decisión de Abraham, 2026-08-24, redefine el brief heredado de #124):
la duplicación TS↔TS ya no existe (desde #130/20260809000007+20260815000005 el
whitelist de APLICACIÓN vive en SQL, dentro de la RPC `moderate_property_atomic`
— `_shared/clients.ts` lo documenta). En vez de migrar datos, se factoriza el
whitelist de `edit-property` a un módulo TS compartido
(`_shared/property_field_whitelist.ts`) y se escribe un test que compara ese
módulo TS **contra la RPC real (SQL)** y **contra lo que edit-property
realmente envía (seam HTTP)** — así, si un campo nuevo se agrega en un lado y
se olvida el otro, la suite truena con un diff de columnas.

### SEAMS (interfaz bajo test)
- `EDITABLE_PROPERTY_FIELDS` — export público de `supabase/functions/_shared/property_field_whitelist.ts`.
- El conjunto de columnas que `moderate_property_atomic` aplica, leído
  directamente del SQL real (`Deno.readTextFile` sobre
  `supabase/migrations/*moderate_property_atomic*.sql`) — NO se toca la DB,
  se parsea el archivo fuente.
- El contrato HTTP de `edit-property` — `handler(req, deps)` exportado de
  `supabase/functions/edit-property/handler.ts` — invocado con fakes DI
  (mismo patrón que `edit-property/handler.test.ts`), capturando el objeto
  `changed_fields` que llega a `revisionUpserter.upsert(...)`.

### Gotcha de las 2 migraciones (documentado en el propio test)
`20260809000007_moderate_property_atomic.sql` y
`20260815000005_moderate_property_atomic_wizard_fields.sql` definen la MISMA
función (`create or replace function public.moderate_property_atomic(...)`,
misma firma). En Postgres eso REEMPLAZA el cuerpo completo — no hay "unión"
de ambas definiciones. El parser del test ordena los archivos candidatos por
nombre (el prefijo `YYYYMMDDHHMMSS` ordena cronológicamente) y usa
EXCLUSIVAMENTE la ÚLTIMA (`20260815000005`) como fuente de verdad — igual que
el catálogo real de Postgres tras aplicar ambas migraciones en orden.

### EDGE CASES (RED)

#### Happy path / guardia principal
- EC-1: `EDITABLE_PROPERTY_FIELDS` (TS) == conjunto de columnas que la RPC
  `moderate_property_atomic` aplica en SQL, parseado de la ÚLTIMA definición
  real (`20260815000005`) vía `p_changed_fields ? '<col>'` — diff legible en
  AMBAS direcciones (`faltan_en_ts` / `sobran_en_ts`) en un solo `assertEquals`.
  Cubre la asimetría en ambos sentidos: un campo agregado a la RPC sin
  replicar en TS (`faltan_en_ts` no vacío) y un campo agregado al whitelist
  TS que la RPC no aplica (`sobran_en_ts` no vacío).
- EC-2: el conjunto de campos que `edit-property` REALMENTE manda como
  `changed_fields` (capturado invocando el `handler` real — no un mock del
  SUT, el módulo de producción — con fakes DI, payload COMPLETO incluyendo
  todos los campos opcionales de #142/wizard paso 3, forzando el camino de
  revisión con `price` distinto) == `EDITABLE_PROPERTY_FIELDS` — mismo diff
  bidireccional (`faltan_en_whitelist` / `sobran_en_whitelist`). Sanity previa
  dentro del mismo test: `res.status === 200` y `revisionUpserter.upsert`
  llamado exactamente 1 vez (si esto fallara, el resto del test no diría nada
  sobre el whitelist).

#### Sanity / boundary
- EC-3: `EDITABLE_PROPERTY_FIELDS` no está vacío y tiene el tamaño real (16
  columnas — contadas a mano en la RPC `20260815000005`: operation_type,
  property_type, price, bedrooms, bathrooms, square_meters,
  built_square_meters, half_bathrooms, currency, address, location,
  price_visible, pet_friendly, allows_no_guarantor, student_friendly,
  description).
- EC-4: `EDITABLE_PROPERTY_FIELDS` coincide con el snapshot LITERAL leído a
  mano de la migración `20260815000005` (fuente de verdad INDEPENDIENTE del
  parser regex de EC-1 — si el regex de EC-1 tuviera un bug que se comiera
  una columna, EC-4 la sigue cazando porque el literal se transcribió a mano
  del archivo, no se derivó con el mismo mecanismo).
