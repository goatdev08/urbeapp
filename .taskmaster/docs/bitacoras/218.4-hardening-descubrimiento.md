## 218.4 — Hardening post-guardian: descubrimiento de la RPC por CONTENIDO, no por nombre de archivo

GREEN ya commiteado en `5bea6e8` (16 columnas llenas, 4/4 EC verdes). El
guardian reportó un punto ciego real en el test de guardia (RED, no en el
módulo `property_field_whitelist.ts`), demostrado con un mutante:
`extract_rpc_changed_fields_columns` (EC-1) descubría los archivos candidatos
por NOMBRE (`/moderate_property_atomic.*\.sql$/`). Una migración futura que
haga `create or replace function public.moderate_property_atomic` desde un
archivo con OTRO nombre (el caso natural: `20260901000000_add_parking_field.sql`,
nombrado por lo que agrega, no por la función que toca) nunca entraba a
`candidatos` — EC-1 seguía comparando contra la definición VIEJA y pasaba en
verde sobre una RPC ya divergente. Mutante del guardian (c1): migración
temporal con timestamp más alto y una columna extra en el CASE — sobrevivía
4/4 con nombre `29990101000000_tmp_mutant.sql`, moría solo si el nombre
contenía `moderate_property_atomic`.

### Diff conceptual del descubrimiento

**Antes (por NOMBRE de archivo):**
```ts
for await (const entry of Deno.readDir(MIGRATIONS_DIR)) {
  if (entry.isFile && /moderate_property_atomic.*\.sql$/.test(entry.name)) {
    candidatos.push(entry.name);
  }
}
...
candidatos.sort();
const ultima = candidatos[candidatos.length - 1];
const sql = await Deno.readTextFile(new URL(ultima, MIGRATIONS_DIR));
```
El regex corría sobre `entry.name` — el contenido del .sql nunca se
inspeccionaba para decidir si el archivo era candidato.

**Después (por CONTENIDO):**
```ts
const DEFINES_MODERATE_PROPERTY_ATOMIC =
  /create\s+or\s+replace\s+function\s+(?:public\.)?moderate_property_atomic\s*\(/i;

for await (const entry of Deno.readDir(MIGRATIONS_DIR)) {
  if (!entry.isFile || !entry.name.endsWith(".sql")) continue;
  const sql = await Deno.readTextFile(new URL(entry.name, MIGRATIONS_DIR));
  if (DEFINES_MODERATE_PROPERTY_ATOMIC.test(sql)) {
    candidatos.push({ name: entry.name, sql });
  }
}
...
candidatos.sort((a, b) => a.name.localeCompare(b.name));
const ultima = candidatos[candidatos.length - 1];
// ultima.sql ya está en memoria — no se re-lee el archivo
```
Ahora se leen TODOS los `.sql` de `supabase/migrations/` y se filtra por si
el CONTENIDO define `moderate_property_atomic` (tolerante a `public.`
opcional y a espacios/saltos de línea entre tokens, case-insensitive — igual
que Postgres trata identifiers sin comillas). El nombre del archivo YA NO
decide si es candidato; solo se sigue usando para el ORDEN "la última gana"
(el prefijo `YYYYMMDDHHMMSS` es la convención real de las migraciones de
Supabase, y sí ordena cronológicamente).

Archivo tocado: **SOLO** `supabase/functions/_shared/property_field_whitelist.test.ts`
(comentario de cabecera actualizado + función `extract_rpc_changed_fields_columns`
reescrita). No se tocó `property_field_whitelist.ts` ni ninguna Edge Function.

### Resultado
Descubrimiento robusto a nombres de archivo arbitrarios; sigue usando el
timestamp del nombre SOLO para el orden "la última gana" entre candidatos
YA confirmados por contenido. No se tocó `property_field_whitelist.ts` ni
ninguna EF — cambio acotado al archivo de test, tal como pidió el
coordinador. Sin commit (lo hace el orquestador como `test(hardening)`
separado).
