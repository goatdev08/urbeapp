Origen: bloqueante documentado por el GREEN en la entrada anterior de esta subtarea

## Defecto y reparación (SOLO andamiaje `act`/`await`, CERO cambio de aserciones)

1. **EC-16** (`error_message_expuesto_tras_fallo_y_limpiado_en_el_siguiente_exito`):
   `rerender({ client: mock_ok.client })` de RNTL se llamaba **sin `await`**, seguido de otro
   `await act(async () => {...})` en el MISMO test. RNTL 14 `rerender` es async (memoria
   `rntl14_renderhook_async`) — mezclar un `rerender` no-awaited con un `act(async)` awaited
   después anida un "act scope" que nunca se asienta, y ese desajuste queda corrupto para los
   tests SIGUIENTES del archivo.
   - **Fix**: `await rerender({ client: mock_ok.client });`.

2. **EC-17/EC-18** (`segunda_llamada_...es_ignorada_sin_segunda_invocacion` /
   `la_llamada_ignorada_no_afecta_el_resultado_de_la_llamada_en_curso`): las dos llamadas a
   `moderate()` arrancaban dentro de `act(() => {...})` **síncrono**. Con React concurrente el
   `act()` síncrono no garantiza que el estado (`is_working_ref` + `force_update`) se aplique
   antes de que el test siga leyendo — y, en cadena con el defecto de EC-16 (mismo archivo,
   mismo entorno de act queue), dejaba el estado interno de RNTL corrupto para EC-19.
   - **Fix**: `await act(async () => {...})` envolviendo el arranque de ambas llamadas,
     dejando la(s) promesa(s) `pending` sin resolver DENTRO de ese `act` — el `release()` de la
     promesa en vuelo sigue en un `act` posterior, como ya estaba. Ninguna llamada se espera
     (`await`) dentro de ese primer bloque: solo se dispara y se deja pendiente, igual que
     antes — el único cambio es que el disparo ahora ocurre dentro de un scope `act` async
     correctamente cerrado en vez de uno síncrono.

3. **EC-19** no tenía defecto propio — quedaba rojo en cascada por la corrupción de estado que
   dejaban EC-16/17/18 al correr antes en el mismo archivo. Se resuelve solo al reparar los
   tres anteriores; no se tocó su código.
